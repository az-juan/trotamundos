# ADR-005: Estrategia de Caché de Aplicación en Memoria de Proceso Go en Fase 0

* Status: accepted
* Deciders: Arquitecto de Software Principal de Trotamundos, Equipo Core de Ingeniería
* Date: 2026-10-28

Technical Story: [QA-1, QA-6, QA-8, CON-C1, CON-C3, CON-5]

## Context and Problem Statement

El panel de gestión de viajes de Trotamundos debe atender a 2 millones de usuarios activos semanales (QA-1) garantizando un tiempo de respuesta de navegación web $\le 800\text{ ms}$ (QA-6), con una meta interna para usuarios recurrentes de p95 $< 300\text{ ms}$. Si bien PostgreSQL 16 es altamente eficiente, ejecutar consultas repetitivas sobre viajes (`GET /trips/{id}`) cada vez que el usuario navega entre pestañas o refresca su pantalla introduce una carga de I/O y latencia innecesaria sobre la base de datos transaccional.

Para mitigar esto, es una práctica estándar introducir una capa de caché de lecturas en caliente. Sin embargo, en Fase 0 el presupuesto de infraestructura es de $\le \$100\text{ USD/mes}$ (CON-C3) y el equipo es acotado (CON-C1). Desplegar un clúster de Redis gestionado en la nube añade un costo recurrente de \$15 a \$30 USD/mes, introduce otro punto de falla de red y requiere configurar clientes de conexión y serialización adicionales.

¿Cómo implementar una estrategia de almacenamiento en caché de alto rendimiento que cumpla con los SLAs de latencia y proteja a la base de datos sin incurrir en costos económicos ni operativos adicionales en Fase 0?

## Decision Drivers

* `QA-6`: Latencia de respuesta en panel web $\le 800\text{ ms}$ (meta p95 $< 300\text{ ms}$ en lecturas en caliente).
* `QA-1`: Reducción de la carga de base de datos ante 2 millones de usuarios activos semanales.
* `QA-8`: Disponibilidad continua, minimizando dependencias de red externas que puedan fallar.
* `CON-C1`: Simplicidad de implementación y cero sobrecarga de mantenimiento.
* `CON-C3`: Presupuesto mensual mínimo, eliminando el alquiler de servicios de caché gestionados en la nube.
* `CON-5`: Iteración II y III de ADD 3.0 (Tecnología y tácticas de calidad).

## Considered Options

* **Opción 1:** Despliegue de un Clúster de Redis Gestionado desde Fase 0
* **Opción 2:** Cero Caché de Aplicación (todas las consultas van directo a PostgreSQL)
* **Opción 3:** Caché In-Memory en el Proceso Go (`ristretto` / `ccache`) encapsulado tras una interfaz de puerto `CacheStore`

## Decision Outcome

Chosen option: **Opción 3: Caché In-Memory en el Proceso Go encapsulado tras una interfaz de puerto `CacheStore`**, porque proporciona lecturas en nanosegundos directamente desde la memoria RAM del proceso Go con costo de infraestructura de **\$0 USD** y cero latencia de red.

Se utiliza una biblioteca madura y de alto rendimiento en Go, como **`dgraph-io/ristretto`** (o `karlseguin/ccache`), que implementa políticas de desalojo eficientes TinyLFU/LRU, límites estrictos de consumo de memoria y concurrencia segura sin bloqueos globales de mutex. Los viajes e itinerarios en caliente se almacenan con un Time-to-Live (TTL) corto (1 a 5 minutos) y se invalidan explícitamente cuando el usuario actualiza una reserva o cuando arriba un evento de sincronización de proveedor.

Siguiendo la **Arquitectura Hexagonal (ADR-001)**, la caché no se acopla directamente al dominio, sino que se define un puerto de salida:
```go
type CacheStore interface {
    Get(ctx context.Context, key string) ([]byte, bool)
    Set(ctx context.Context, key string, value []byte, ttl time.Duration)
    Delete(ctx context.Context, key string)
}
```
En Fase 0, la implementación de este puerto es el adaptador local en memoria. Si en Fase 1 o Fase 2 el sistema escala horizontalmente a múltiples réplicas que requieran invalidación distribuida coordinada, se sustituye el adaptador por uno basado en **Redis** sin alterar una sola línea de lógica de negocio ni use cases.

### Positive Consequences

* **Costo Cero Absoluto (CON-C3):** No se contratan instancias de Redis gestionadas ni contenedores adicionales, ahorrando presupuesto crítico para el proyecto.
* **Rendimiento Máximo en Lecturas (QA-6):** Las consultas cacheadas se resuelven en microsegundos dentro del espacio de memoria del proceso Go, sin saltos de red TCP ni serialización remota (p95 $< 50\text{ ms}$).
* **Menor Carga en PostgreSQL (QA-1):** Se reduce en más de un 70% el tráfico de lectura sobre las tablas relacionales de viajes.
* **Cero Complejidad de Red y Alta Confiabilidad (QA-8):** Al no haber un servidor de caché externo por la red, no existen caídas de conexión, reconexiones ni timeouts de socket que degraden el servicio.
* **Extensibilidad a Redis Garantizada:** La abstracción tras el puerto `CacheStore` asegura que la migración futura a Redis sea puramente un cambio de configuración en el arranque del servicio.

### Negative Consequences

* **Caché Local por Instancia:** Si el binario corre en múltiples réplicas en el futuro, cada instancia mantiene su propia caché local y una actualización en una réplica podría tardar el tiempo del TTL en reflejarse en otra (mitigado porque en Fase 0 se despliega en una única instancia en el servidor).
* **Consumo de Memoria en el Proceso Go:** Debe configurarse un límite máximo de memoria (ej. 100 MB de RAM asignados a `ristretto`) para evitar que la caché compita con el procesamiento de la aplicación.

## Pros and Cons of the Options

### Opción 1: Clúster de Redis Gestionado desde Fase 0

* Good, because caché centralizada compartida automáticamente entre múltiples réplicas.
* Good, because permite pub/sub y estructuras de datos avanzadas.
* Bad, because costo mensual extra (\$15–\$30 USD/mes) que erosiona el presupuesto limitado de CON-C3.
* Bad, because introduce latencia de red adicional (1–3 ms) por cada lectura en comparación con la memoria local del proceso.
* Bad, because añade un punto de falla externo que requiere monitoreo, autenticación y gestión de reconexión.

### Opción 2: Cero Caché de Aplicación

* Good, because es la opción más sencilla posible: la base de datos es la única fuente de verdad inmediata sin problemas de invalidación.
* Bad, because cualquier pico de usuarios recurrentes consultando el panel web satura el pool de conexiones de PostgreSQL.
* Bad, because desperdicia CPU de base de datos recalculando agregaciones de viajes que no han cambiado en los últimos minutos.
* Bad, because compromete el cumplimiento holgado del SLA de p95 $< 300\text{ ms}$ en navegación interactiva (QA-6).

### Opción 3: Caché In-Memory en Go tras Interfaz CacheStore

* Good, because latencias de lectura en nanosegundos directamente en RAM de Go.
* Good, because costo económico de \$0 USD adicionales.
* Good, because elimina puntos de falla de red entre la app y la caché.
* Good, because diseño desacoplado listo para cambiar a Redis cuando la escala lo demande.
* Bad, because no comparte estado entre múltiples procesos distintos sin un protocolo de sincronización.
