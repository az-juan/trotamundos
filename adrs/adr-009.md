# ADR-009: Desarrollo de Clientes Móviles Nativos con SwiftUI y Jetpack Compose

* Status: accepted
* Deciders: Arquitecto de Software Principal de Trotamundos, Equipo Core de Ingeniería
* Date: 2026-10-28

Technical Story: [FR-1, FR-4, FR-6, QA-7, QA-13, QA-14, CON-C1, CON-5]

## Context and Problem Statement

Trotamundos se concibe como un panel de gestión de viajes accesible tanto en navegadores de escritorio como en teléfonos móviles inteligentes (QA-14). Los viajeros utilizan intensivamente el dispositivo móvil durante sus traslados (aeropuertos, estaciones de tren, check-in de hoteles), requiriendo un despliegue ultra veloz de su itinerario ($< 1.4\text{ s}$ en primer pintado útil, QA-7) e integración fluida con capacidades del dispositivo como geolocalización GPS y notificaciones nativas (QA-13).

La aplicación móvil debe consumir APIs REST compactas expuestas por el backend en Go. Se debe elegir la estrategia de desarrollo para los clientes móviles considerando rendimiento, experiencia del usuario y mantenibilidad.

¿Qué tecnología y enfoque de desarrollo móvil garantiza la menor latencia de primer despliegue ($< 1.4\text{ s}$), el mejor aprovechamiento del hardware del dispositivo y una experiencia táctil de primer nivel?

## Decision Drivers

* `QA-7`: Primer despliegue de contenido útil en móvil (*First Contentful Paint*) en $< 1.4\text{ segundos}$.
* `QA-13`: Interfaz simple, ágil y ergonómica con soporte nativo para geolocalización GPS.
* `QA-14`: Canales dedicados optimizados tanto para Web como para Móvil.
* `CON-C1`: Simplicidad para conectar con las APIs en Go sin intermediarios propietarios.
* `CON-5`: Iteración II de ADD 3.0 (Funcionalidad primaria y selección tecnológica).

## Considered Options

* **Opción 1:** Aplicación Híbrida Web embebida (*WebView / Capacitor / Cordova*) reutilizando el frontend web
* **Opción 2:** Framework Multiplataforma Híbrido (React Native / Flutter)
* **Opción 3:** Aplicaciones Móviles Nativas Declarativas: **SwiftUI** (iOS) y **Jetpack Compose** (Android) consumiendo endpoints JSON optimizados

## Decision Outcome

Chosen option: **Opción 3: Aplicaciones Móviles Nativas con SwiftUI (iOS) y Jetpack Compose (Android)**, porque garantiza el cumplimiento estricto del SLA de arranque en $< 1.4\text{ s}$ (QA-7) y acceso nativo sin overhead a geolocalización y hardware (QA-13).

Tanto SwiftUI como Jetpack Compose son los estándares modernos y oficiales de Apple y Google:
- Utilizan paradigmas reactivos declarativos modernos similares que facilitan la paridad de arquitectura cliente (MVVM).
- Compilan a código nativo de máquina, eliminando puentes de comunicación JavaScript (*JS bridges*) y motores de renderizado intermedios.
- El backend en Go expone endpoints JSON dedicados y compactos (`/api/v1/mobile/...`), entregando DTOs agregados diseñados específicamente para pantallas móviles, minimizando el consumo de batería y datos móviles 4G/5G.

### Positive Consequences

* **Arranque en Frío Ultrarrápido (QA-7):** Al no cargar WebViews ni motores de JavaScript, la aplicación nativa pinta el contenido del itinerario en $< 0.8\text{ segundos}$, superando con holgura el límite de 1.4 s.
* **Integración Nativa con Sensores y GPS (QA-13):** Acceso directo y sin fricción a CoreLocation en iOS y FusedLocationProvider en Android para contextualizar el viaje del usuario según su ubicación física.
* **Experiencia de Usuario Fluida:** Animaciones nativas a 60/120 fps, soporte nativo de gestos táctiles y transiciones fluidas.

### Negative Consequences

* **Doble Base de Código en Cliente:** Requiere mantener dos proyectos independientes (Swift para iOS y Kotlin para Android). Se mitiga compartiendo contratos formales de API definidos en OpenAPI y lógica de sincronización estándar.

## Pros and Cons of the Options

### Opción 1: WebView Embebida

* Good, because permite reutilizar el 100% del código web HTML sin desarrollar apps nativas.
* Bad, because rendimiento tosco, latencia de renderizado lenta que viola el límite de 1.4 s de QA-7.
* Bad, because soporte deficiente para gestos táctiles nativos e integración torpe con geolocalización.

### Opción 2: Framework Multiplataforma (Flutter / React Native)

* Good, because una sola base de código para ambas plataformas.
* Bad, because añade un runtime pesado que incrementa el peso del binario de la app y ralentiza el inicio en frío.
* Bad, because fricción al actualizar versiones de sistemas operativos móviles o al acceder a APIs de plataforma nativas.

### Opción 3: SwiftUI y Jetpack Compose Nativos

* Good, because máxima velocidad de ejecución y menor tiempo de inicio del mercado.
* Good, because soporte oficial garantizado a largo plazo por Apple y Google.
* Good, because consumo mínimo de batería y memoria en los dispositivos de los viajeros.
* Bad, because exige programar en Swift y Kotlin para cada plataforma.
