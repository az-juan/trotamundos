# ADR-011: Despliegue y Orquestación en Fase 0 con Docker Compose y Servidor Único en DigitalOcean

* Status: accepted
* Deciders: Arquitecto de Software Principal de Trotamundos, Equipo Core de Ingeniería
* Date: 2026-10-28

Technical Story: [QA-8, QA-12, CON-C1, CON-C2, CON-C3, CON-4, CON-5]

## Context and Problem Statement

El prototipo ejecutable de Trotamundos (CON-4) debe pasar de los entornos de desarrollo locales a un entorno de producción accesible en la nube para validar la propuesta de valor con usuarios y clientes B2B. El sistema debe garantizar alta disponibilidad continua (99.988%, QA-8), despliegues automatizados y reproducibles (QA-12) y TLS automático.

Sin embargo, el proyecto está severamente limitado por las restricciones de negocio de `constraints.md`: el equipo cuenta con solo 3 a 5 desarrolladores (CON-C1), el tiempo es crítico (CON-C2) y el presupuesto total de infraestructura es de $\le \$100\text{ USD/mes}$ (CON-C3). Adoptar herramientas avanzadas como Kubernetes (K8s / EKS / GKE), clústeres multi-región o herramientas complejas de GitOps en esta etapa añadiría una sobrecarga de configuración inmensa, requeriría contratar ingenieros DevOps dedicados y consumiría un presupuesto mensual superior a los \$200–\$400 USD solo en plano de control.

¿Qué arquitectura y herramientas de despliegue físico permiten orquestar la solución en producción de forma reproducible, segura y con reinicio automático, manteniendo el costo total mensual por debajo de los \$80–\$100 USD y con cero sobrecarga operativa para el equipo?

## Decision Drivers

* `CON-C3`: Presupuesto mensual de infraestructura estrictamente acotado ($\le \$100\text{ USD/mes}$).
* `CON-C1`: Simplicidad para ser operado y mantenido por 3–5 desarrolladores sin equipo DevOps dedicado.
* `CON-C2`: Puesta en marcha rápida del entorno de producción.
* `CON-4`: Presentar una implementación de prototipo ejecutable tras las 4 iteraciones de diseño.
* `QA-8`: Disponibilidad operacional continua con reinicio automático ante caídas de procesos.
* `QA-12`: Automatización y reproducibilidad de compilaciones y pruebas mediante integración continua (CI/CD).
* `CON-5`: Iteración IV de ADD 3.0 (Despliegue físico, infraestructura y mejoras).

## Considered Options

* **Opción 1:** Plataforma como Servicio Serverless / PaaS Propietaria (AWS ECS Fargate / Heroku / Vercel + bases de datos cloud)
* **Opción 2:** Clúster de Kubernetes Gestionado (DigitalOcean DOKS o AWS EKS) con Terraform y ArgoCD desde Fase 0
* **Opción 3:** Servidor Único en la Nube (DigitalOcean Droplet de 4 a 8 GB RAM / Hetzner) orquestado con **Docker Compose** + **PostgreSQL Gestionado** + CI/CD con **GitHub Actions** y Proxy Reverso **Nginx** con TLS Let's Encrypt

## Decision Outcome

Chosen option: **Opción 3: Servidor Único en DigitalOcean con Docker Compose, PostgreSQL Gestionado y GitHub Actions**, porque es la solución más económica, confiable y fácil de operar que satisface al 100% las restricciones del proyecto.

1. **Topología de Infraestructura (Fase 0)**:
   - **1 Servidor VPS (DigitalOcean Droplet)**: 4 a 8 GB de RAM y 2 a 4 vCPU (\$24 a \$48 USD/mes). Aloja el contenedor del binario compilado en Go de Trotamundos, el contenedor ligero de NATS JetStream ($\sim 30\text{ MB}$ RAM) y un contenedor de Nginx como proxy reverso y terminador TLS.
   - **PostgreSQL 16 Gestionado en DigitalOcean** (\$15 a \$25 USD/mes): Alta disponibilidad, copias de seguridad automáticas diarias y discos SSD rápidos sin carga de mantenimiento para el equipo.
   - **Costo Mensual Total**: $\approx \$45\text{--}\$75\text{ USD/mes}$, cumpliendo con creces la cota de \$100 USD/mes de CON-C3.
2. **Orquestación y Auto-Recuperación**:
   - `docker-compose.yml` sirve como fuente única de verdad para el despliegue tanto en local como en producción.
   - Políticas de reinicio `restart: always` en todos los contenedores para garantizar que si un proceso falla o el servidor se reinicia, los servicios se restablezcan de forma autónoma en segundos (QA-8).
3. **Automatización de Despliegues (CI/CD)**:
   - Pipeline automatizado en **GitHub Actions** ante `push` a la rama `main`:
     1. Ejecución de pruebas unitarias (`go test ./...`) y linters.
     2. Verificación estricta de sintaxis de contratos (`openapi.yaml` y `events.yaml`).
     3. Compilación de imagen Docker optimizada en Go (imagen basada en `alpine` o `distroless`, $< 25\text{ MB}$).
     4. Despliegue continuo vía SSH al Droplet ejecutando `docker compose pull && docker compose up -d`. Tiempo total de despliegue: $< 90\text{ segundos}$.

**Criterios de Migración a Kubernetes / K3s (Fase 2)**:
Se migrará a un clúster K3s gestionado únicamente si se cumplen al menos 2 de las siguientes condiciones:
1. El equipo de ingeniería supera los 8 desarrolladores y los despliegues simultáneos generan cuellos de botella de coordinación.
2. Un módulo extraído como microservicio requiere auto-escalado horizontal programático basado en métricas (HPA/KEDA).
3. Se requiere presencia multi-región por exigencias de latencia o cumplimiento normativo internacional.

### Positive Consequences

* **Costo Predecible y Mínimo (CON-C3):** Gasto controlado de $\approx \$60\text{ USD/mes}$, dejando margen presupuestario para imprevistos.
* **Operación Trivial para el Equipo (CON-C1):** Cero necesidad de aprender conceptos complejos de Kubernetes (Pods, Ingress Controllers, CNI, PersistentVolumes); cualquier desarrollador comprende Docker Compose.
* **Arranque Rápido y Despliegues en Menos de 2 Minutos:** Compilación nativa en Go y actualización de contenedores sin fricción.
* **Seguridad Automática:** Nginx renueva automáticamente los certificados SSL/TLS mediante Certbot / Let's Encrypt sin intervención manual.

### Negative Consequences

* **Escalado Vertical Inicial:** Ante incrementos masivos de carga, el escalado en Fase 0 se realiza aumentando los recursos del servidor Droplet (resizing vertical en 2 minutos desde el panel de DigitalOcean) en lugar de auto-escalado horizontal elástico.
* **Punto Único de Fallo en Compute:** Al correr en un único servidor VPS, una caída física de la máquina virtual dejaría el servicio inactivo hasta que el hipervisor lo reinicie (mitigado con monitoreo externo en UptimeRobot y backups diarios en la base de datos gestionada).

## Pros and Cons of the Options

### Opción 1: Plataforma Serverless / PaaS Propietaria

* Good, because no requiere administrar servidores ni configurar Nginx.
* Bad, because costos ocultos crecientes por ancho de banda, ejecuciones y almacenamiento que escalan impredeciblemente.
* Bad, because problemas de arranque en frío (*cold starts*) de funciones serverless que atentan contra el SLA de 800 ms de QA-6.
* Bad, because acoplamiento y dependencia con un proveedor cloud propietario (*vendor lock-in*).

### Opción 2: Kubernetes Gestionado desde Fase 0

* Good, because auto-escalado horizontal elástico y autoreparación avanzada de pods.
* Bad, because costo mínimo mensual que supera los \$150–\$250 USD solo en infraestructura base (violando CON-C3).
* Bad, because curva de aprendizaje enorme y sobrecarga de mantenimiento que desvía al equipo del desarrollo del producto (violando CON-C1 y CON-C2).

### Opción 3: Docker Compose en DigitalOcean + PostgreSQL Gestionado

* Good, because costo mínimo y predecible de \$45 a \$75 USD/mes.
* Good, because idéntica configuración entre el entorno local de desarrollo y el servidor de producción.
* Good, because simplicidad de operación para un equipo pequeño sin perfiles DevOps dedicados.
* Good, because pipeline de CI/CD en GitHub Actions probado y reproducible.
* Bad, because requiere escalar verticalmente el servidor antes de requerir orquestación multi-nodo en Fase 2.
