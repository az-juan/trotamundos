# ADR-007: Autenticación Stateless mediante JWT con Secreto Simétrico en Fase 0

* Status: accepted
* Deciders: Arquitecto de Software Principal de Trotamundos, Equipo Core de Ingeniería
* Date: 2026-10-28

Technical Story: [FR-1, FR-4, FR-8, QA-9, QA-10, QA-14, CON-C1, CON-C3, CON-5]

## Context and Problem Statement

Trotamundos debe autenticar y autorizar a los viajeros que acceden al panel de viajes tanto desde el navegador web como desde aplicaciones móviles nativas en iOS y Android (QA-14). El sistema debe proteger las reservas y los datos personales de los usuarios (QA-9), permitir compartir itinerarios mediante enlaces seguros con permisos controlados (QA-10) y validar la identidad del usuario en cada petición HTTP sin introducir latencias que comprometan el SLA de 800 ms (QA-6).

En las fases tempranas de un producto (Fase 0 / MVP), el equipo está compuesto por 3 a 5 desarrolladores (CON-C1) y el presupuesto es de $\le \$100\text{ USD/mes}$ (CON-C3). Introducir un servidor de identidad independiente y dedicado (como Keycloak, Ory Kratos o servicios SaaS de pago como Auth0) añade una sobrecarga de infraestructura masiva (Keycloak exige $> 1\text{ GB}$ de RAM en JVM) y complejidad de integración desproporcionada. Por otro lado, usar sesiones tradicionales almacenadas en la base de datos PostgreSQL obligaría a realizar una consulta SQL de verificación en cada request HTTP que realice el usuario, saturando el pool de conexiones de la base de datos ante 2 millones de usuarios semanales (QA-1).

¿Cómo implementar un mecanismo de autenticación seguro, liviano y estandarizado para clientes web y móviles que valide credenciales en microsegundos sin sobrecargar la base de datos ni requerir servidores de identidad adicionales en Fase 0?

## Decision Drivers

* `QA-9`: Acceso seguro y autorizado a las reservas y datos del usuario sin exponer contraseñas ni tokens en claro.
* `QA-10`: Restricción estricta de permisos de visualización al compartir itinerarios.
* `QA-14`: Soporte unificado y sin fricción tanto para el frontend Web como para apps nativas Móviles.
* `QA-6`: Latencia mínima de validación en cada petición HTTP ($< 1\text{ ms}$).
* `QA-1`: Escalabilidad ante 2 millones de usuarios activos sin generar consultas de sesión contra PostgreSQL.
* `CON-C1`: Simplicidad de implementación en Go mediante bibliotecas estándar probadas.
* `CON-C3`: Costo de infraestructura \$0 adicional.
* `CON-5`: Iteración III de ADD 3.0 (Tácticas de seguridad y autenticación).

## Considered Options

* **Opción 1:** Servidor de Identidad Dedicado (Keycloak / Ory / Auth0) desde Fase 0
* **Opción 2:** Sesiones Tradicionales con Estado (*Stateful Sessions*) almacenadas en PostgreSQL
* **Opción 3:** Autenticación Stateless con Tokens JWT firmados mediante HMAC-SHA256 (HS256) validados en memoria por middleware en Go

## Decision Outcome

Chosen option: **Opción 3: Autenticación Stateless con Tokens JWT firmados mediante HMAC-SHA256 (HS256) validados en memoria por middleware en Go**, porque proporciona autenticación ultra veloz, escalable y con costo de infraestructura de **\$0 USD**.

El backend de Trotamundos emite un token JWT firmado tras la autenticación de credenciales o el flujo OAuth2 con Google/Microsoft. El token contiene los *claims* esenciales: identificador del usuario (`sub`), roles, identificador de correlación y fecha de expiración (`exp` fijada a 24 horas). En cada petición entrante (cabecera `Authorization: Bearer <token>` o cookie HTTP-only segura en web), un middleware de Chi en Go (`golang-jwt/jwt/v5`) valida la firma criptográfica puramente en CPU y memoria en **menos de 0.1 ms**, extrayendo el ID del usuario y colocándolo en el `context.Context` de la petición.

**Regla de Extracción Futura a Fase 2**:
Cuando la base de usuarios crezca, el equipo supere los 8 desarrolladores y se requieran flujos de login social complejos con rotación avanzada de refresh tokens, se extraerá el módulo de autenticación a un servicio independiente **`Identity Service`** basado en OpenID Connect (OIDC) y tokens asimétricos RS256 con endpoints JWKS, sin modificar los endpoints de dominio que ya esperan el contexto de usuario autenticado.

### Positive Consequences

* **Cero Carga en PostgreSQL (QA-1):** Validar si una petición está autenticada no toca la base de datos; la verificación matemática de la firma HMAC ocurre íntegramente en la memoria de Go.
* **Latencia Despreciable (QA-6):** La verificación del JWT toma menos de 100 microsegundos, protegiendo con holgura el SLA de 800 ms.
* **Compatibilidad Total Multicanal (QA-14):** Funciona idénticamente para clientes Web (enviado en cookie segura o cabecera) y aplicaciones nativas iOS/Android (enviado en cabecera `Authorization`).
* **Cero Costo de Servidores (CON-C3):** No se requieren instancias adicionales de Keycloak ni suscripciones mensuales a proveedores SaaS de Auth.
* **Control Fino de Permisos para Itinerarios Compartidos (QA-10):** Permite generar tokens JWT específicos con alcance limitado (*scope: share_read*) para compartir itinerarios públicos o restringidos sin dar acceso a la cuenta global del viajero.

### Negative Consequences

* **Revocación Inmediata Más Compleja:** Al ser un token stateless, no se puede invalidar instantáneamente antes de su expiración sin consultar una lista de revocación (mitigado con un tiempo de vida corto del token de 24 horas y almacenamiento de lista negra en memoria local en caso de cierre de sesión forzado).
* **Secreto Simétrico Compartido:** El secreto de firma debe protegerse celosamente en variables de entorno seguras del servidor (mitigado mediante inyección de variables de entorno en el despliegue de Docker).

## Pros and Cons of the Options

### Opción 1: Servidor de Identidad Dedicado (Keycloak / Ory / Auth0)

* Good, because provee funcionalidades avanzadas listas para usar (consola de administración de usuarios, 2FA, reseteo de claves).
* Bad, because Keycloak demanda mínimo 1 GB de RAM en una JVM pesada, duplicando el consumo de recursos de todo el sistema en Fase 0 (violando CON-C3).
* Bad, because añade una sobrecarga de configuración y aprendizaje enorme para un equipo pequeño de 3–5 desarrolladores (violando CON-C1).
* Bad, because proveedores SaaS como Auth0 imponen costos crecientes por usuario activo mensual que rompen la restricción de presupuesto.

### Opción 2: Sesiones Stateful con Almacenamiento en Base de Datos

* Good, because revocación de sesiones instantánea borrando la fila en la tabla de sesiones.
* Good, because modelo tradicional muy conocido.
* Bad, because cada petición HTTP entrante requiere ejecutar una consulta `SELECT * FROM sessions WHERE id = ...` en PostgreSQL, saturando el pool de conexiones ante millones de peticiones (violando QA-1).
* Bad, because no es idiomático para clientes móviles nativos que prefieren tokens de portador (*bearer tokens*).

### Opción 3: JWT Stateless en Memoria con Go

* Good, because validación ultra rápida en memoria en $< 0.1\text{ ms}$.
* Good, because cero consultas a PostgreSQL en cada petición.
* Good, because costo de \$0 USD y cero dependencias de servidores externos.
* Good, because funciona naturalmente en web y móvil.
* Bad, because la revocación previa al vencimiento requiere gestionar una lista negra de tokens revocados.
