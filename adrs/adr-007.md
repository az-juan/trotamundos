## ADR-007: Resiliencia en Integraciones Externas

**Status**: Propuesto
**Fecha**: 2026-10-26
**Decidido por**: Equipo de arquitectura

### Contexto

El servicio de Integration consume APIs de aerolíneas, hoteles y rentadoras. Estas APIs tienen: rate limits distintos, tiempos de respuesta variables, caídas intermitentes, y formatos de error no estandarizados. Un fallo en un proveedor no puede tumbar el panel.

### Decisión

Cada adaptador de salida (proveedor) usa una **cadena de resiliencia** con decoradores:

```
Request → CircuitBreaker (sony/gobreaker) → Retry (go-retryablehttp, backoff + jitter) → RateLimiter (x/time/rate) → HTTP Client (context timeout)
```

| Parámetro | Valor |
|-----------|-------|
| Circuit breaker: trip | 5 fallos consecutivos |
| Circuit breaker: open duration | 30 s |
| Retry: max attempts | 3 |
| Retry: backoff | Exponential (1s, 2s, 4s) + jitter ±20% |
| Retry: condiciones | 429, 5xx, timeout (no 4xx) |
| Rate limit | Por proveedor (p.ej. 10 req/s Amadeus, 5 req/s HotelChain) |
| Timeout | 5 s (aerolíneas), 10 s (hoteles), 3 s (rentadoras) |

Webhooks entrantes: verificación de firma + idempotencia (SHA256 en Redis, TTL 24 h).

### Consecuencias

| Positivas | Negativas / Riesgos |
|-----------|-------------------|
| Un proveedor caído no afecta a los otros ni al panel | Complejidad: 4 librerías por adaptador (mitigado: wrapper `ResilientClient` en `shared/`) |
| SLA de 800 ms protegido: el timeout es estricto | Si todos los proveedores caen → el panel muestra "datos desactualizados" (graceful degradation) |
| Observabilidad: métricas de breaker state, retry count, rate limit hits (Prometheus) | |
