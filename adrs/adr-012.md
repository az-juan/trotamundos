# ADR-012: Adopción del Enfoque Spec-Driven Development (SDD) con OpenAPI 3.1, JSON Schema y oapi-codegen

* Status: accepted
* Deciders: Arquitecto de Software Principal de Trotamundos, Equipo Core de Ingeniería
* Date: 2026-10-28

Technical Story: [FR-1, FR-4, FR-6, QA-4, QA-11, QA-12, CON-1, CON-4, CON-5]

## Context and Problem Statement

Trotamundos integra múltiples componentes y canales: clientes web en servidor, aplicaciones móviles nativas (iOS y Android), adaptadores para APIs externas de transporte y eventos asíncronos que circulan entre módulos de dominio. En equipos de desarrollo de software ágiles, es común que la documentación de las APIs se desactualice respecto a la implementación (*documentation drift*), provocando errores de integración entre frontend y backend, discordancia en los tipos de datos y retrasos en la depuración.

La directiva arquitectónica **CON-1** formalizada en `./drivers/concerns.md` exige explícitamente: *"Realizar un proceso de ADD de 4 iteraciones para Trotamundos usando Spec-Driven Development (SDD)"*. Además, la directiva **QA-12** requiere alta trazabilidad y testeabilidad.

¿Cómo garantizar que las interfaces síncronas HTTP y los eventos asíncronos mantengan contratos formales inmutables y verificables en tiempo de compilación sin duplicar esfuerzos manuales de documentación para un equipo pequeño?

## Decision Drivers

* `CON-1`: Adopción obligatoria de Spec-Driven Development (SDD) como metodología rectora.
* `QA-12`: Alta trazabilidad, observabilidad y facilidad de pruebas para el código y las interfaces.
* `QA-4`: Interoperabilidad con contratos claros frente a clientes móviles y externos.
* `QA-11`: Modificabilidad sin regresiones mediante contratos tipados estrictamente.
* `CON-C1`: Simplicidad y reducción de errores manuales para un equipo pequeño de 3 a 5 desarrolladores.
* `CON-5`: Iteración II y IV de ADD 3.0 (Definición de contratos y preparación del prototipo CON-4).

## Considered Options

* **Opción 1:** Enfoque *Code-First* tradicional (escribir controladores y structs en Go primero y documentar manualmente o mediante comentarios anotados)
* **Opción 2:** Adopción de gRPC / Protocol Buffers para todas las comunicaciones internas y externas
* **Opción 3:** Enfoque *Spec-Driven Development* (SDD / *Contract-First*) con **OpenAPI 3.1** para APIs síncronas (compilado con `oapi-codegen` a interfaces estrictas en Go) y **JSON Schema** para el catálogo de eventos en NATS JetStream

## Decision Outcome

Chosen option: **Opción 3: Enfoque Spec-Driven Development (SDD / Contract-First) con OpenAPI 3.1, oapi-codegen y JSON Schema**, porque convierte las especificaciones en la **única fuente de verdad** ejecutable del proyecto antes de escribir código de implementación.

1. **APIs Síncronas (HTTP / REST)**:
   - Se diseñan y versionan en `docs/api/openapi.yaml` bajo el estándar **OpenAPI 3.1**.
   - La herramienta oficial de Go **`oapi-codegen`** genera en tiempo de compilación los tipos de datos (`structs`), los validadores de parámetros y las interfaces del servidor (`StrictServerInterface`) para el router Chi.
   - Si la implementación en Go no satisface exactamente los parámetros, rutas o códigos de respuesta definidos en el YAML, el compilador arroja un error impidiendo compilar el binario.
2. **Eventos Asíncronos (NATS JetStream)**:
   - Se especifican formalmente en `docs/events/events.yaml` mediante **JSON Schema**, documentando cada campo, tipo y cabecera de idempotencia (ULID).
   - En tiempo de ejecución y pruebas unitarias (`go test`), el paquete `shared/event` valida los payloads de los mensajes contra sus esquemas JSON antes de publicarlos o procesarlos.
3. **Consumo en Clientes Móviles**:
   - Los contratos OpenAPI sirven para generar directamente los clientes de red en Swift (iOS) y Kotlin (Android), garantizando compatibilidad total sin desajustes.

### Positive Consequences

* **Cero Drift de Documentación (CON-1):** El código fuente de las rutas y tipos es un subproducto derivado de la especificación; la documentación nunca queda desactualizada porque el código no compila si no coincide.
* **Seguridad de Tipos Rigurosa:** Errores como parámetros faltantes, nombres mal escritos o tipos de datos incorrectos son detectados inmediatamente por el compilador de Go.
* **Integración sin Fricción Frontend/Backend:** Los desarrolladores móviles y de backend acuerdan el contrato YAML primero, permitiendo trabajar en paralelo sin bloqueos mutuos.
* **Validación Automatizada en CI (QA-12):** El pipeline de GitHub Actions verifica la sintaxis de los archivos OpenAPI y JSON Schema en cada commit antes de permitir el merge.

### Negative Consequences

* **Disciplina de Especificación Previa:** Los desarrolladores no pueden crear endpoints ni eventos directamente en código Go sin haber actualizado primero el archivo de especificación en YAML.

## Pros and Cons of the Options

### Opción 1: Enfoque Code-First Tradicional

* Good, because permite a los desarrolladores empezar a programar código Go de inmediato sin aprender la sintaxis de OpenAPI.
* Bad, because la documentación Swagger generada por anotaciones de código es propensa a quedar desactualizada rápidamente.
* Bad, because traslada la detección de errores de integración al momento de ejecución o pruebas manuales.
* Bad, because viola la directiva fundacional CON-1 del proyecto Trotamundos.

### Opción 2: gRPC y Protocol Buffers para Todo

* Good, because serialización binaria ultrarrápida y contratos estrictos `.proto`.
* Bad, because gRPC no es amigable para navegadores web ni para inspección directa en HTTP estándar sin proxies adicionales (gRPC-Web).
* Bad, because añade una curva de aprendizaje innecesaria para un equipo pequeño y complica la depuración con herramientas como curl o Postman.

### Opción 3: Spec-Driven Development con OpenAPI 3.1 y JSON Schema

* Good, because estándar abierto universal de la industria para APIs web y móviles.
* Good, because `oapi-codegen` genera código Go limpio y type-safe para Chi.
* Good, because JSON Schema formaliza los eventos de NATS garantizando idempotencia y orden.
* Good, because satisface plenamente CON-1, CON-4 y QA-12.
* Bad, because exige mantener archivos YAML de especificación con rigor.
