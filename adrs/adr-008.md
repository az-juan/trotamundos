# ADR-008: Ingesta de Correo Electrónico mediante Gmail API + IMAP y Parser Determinístico por Reglas

* Status: accepted
* Deciders: Arquitecto de Software Principal de Trotamundos, Equipo Core de Ingeniería
* Date: 2026-10-28

Technical Story: [FR-2, FR-3, QA-3, QA-4, QA-9, CON-C1, CON-C2, CON-C3, CON-5]

## Context and Problem Statement

Uno de los requerimientos funcionales medulares de Trotamundos es la captura y escaneo automatizado de reservas directamente desde las bandejas de correo electrónico de los usuarios (FR-2). Los viajeros utilizan servicios heterogéneos (Gmail, Outlook/Office365, proveedores IMAP corporativos y genéricos). Los correos de confirmación no poseen un formato estructurado universal: son cuerpos MIME con HTML y texto plano con variaciones constantes según la aerolínea, hotel o agencia emisora.

El proceso de escaneo y parseo debe ser seguro (QA-9), soportar ráfagas masivas de cancelaciones sin colapsar (QA-3) y permitir discriminar remitentes seguros mediante listas blancas (FR-3). Además, el presupuesto de desarrollo y operación es acotado (CON-C3). Incorporar modelos de lenguaje comerciales (LLMs vía APIs externas de OpenAI/Anthropic) para parsear cada correo recibido introduciría un costo recurrente prohibitivo (superando fácilmente los \$0.01–\$0.03 USD por correo analizado), además de añadir latencias de segundos y riesgos de privacidad (QA-9).

¿Qué arquitectura y tecnologías de conexión, autenticación y extracción de datos deben adoptarse para procesar correos electrónicos con máxima velocidad, bajo costo y total determinismo?

## Decision Drivers

* `FR-2`: Captura automática de reservas desde bandejas de correo electrónico.
* `FR-3`: Creación y aplicación de *whitelists* de remitentes seguros.
* `QA-9`: Acceso seguro, revocado y con mínimos privilegios a las bandejas del usuario.
* `QA-3`: Aislamiento y amortiguación de ráfagas masivas de correos durante eventos climáticos o cancelaciones.
* `CON-C1`: Simplicidad para ser mantenido por un equipo pequeño en Go.
* `CON-C3`: Costo operacional cercano a \$0 USD en procesamiento.
* `CON-5`: Iteración II de ADD 3.0 (Funcionalidad primaria y selección tecnológica).

## Considered Options

* **Opción 1:** Polling agresivo constante mediante POP3/IMAP con parseo delegado a APIs comerciales de LLMs (OpenAI/Anthropic)
* **Opción 2:** Conexión manual por subida de archivos `.eml` por parte del usuario (sin automatización)
* **Opción 3:** Conexión Híbrida Push/Pull (**Gmail API Push** + **IMAP IDLE**) con Deduplicación en Memoria/DB y **Pipeline de Parseo Determinístico por Reglas/Regex** en Go

## Decision Outcome

Chosen option: **Opción 3: Conexión Híbrida Push/Pull con Deduplicación y Parser Determinístico por Reglas en Go**, porque maximiza la reactividad, garantiza costo \$0 en cómputo y protege la privacidad del viajero.

1. **Protocolos de Conexión**:
   - **Gmail**: Se utiliza la API oficial de Google (`google.golang.org/api/gmail/v1`) con notificaciones push mediante Google Cloud Pub/Sub hacia un webhook de Trotamundos, eliminando el polling continuo. Autenticación delegada vía **OAuth2** con scope estricto de solo lectura (`gmail.readonly`).
   - **Outlook e IMAP Genérico**: Se utiliza la biblioteca nativa en Go `emersion/go-imap/v2` con extensiones **IDLE** (push sobre socket TCP) para proveedores compatibles, y polling de respaldo cada 60 segundos únicamente para servidores que no soporten IDLE. Autenticación con **XOAUTH2** y tokens cifrados en reposo en PostgreSQL.
2. **Deduplicación Previa al Parseo**:
   - Para no gastar CPU innecesaria ante reescaneos, se calcula el hash criptográfico $\text{SHA256}(\text{From} + \text{Subject} + \text{Date})$. Si el hash ya existe en la tabla de deduplicación de PostgreSQL o en la caché en memoria, el correo se descarta en microsegundos.
3. **Pipeline de Extracción por Reglas (Fase 0)**:
   - Parseo MIME nativo con la librería estándar de Go `net/mail`.
   - Se procesan los correos cuyos remitentes coincidan con la *whitelist* (FR-3).
   - Extracción de datos (fechas, códigos PNR, nombres de aerolíneas, números de vuelo) mediante expresiones regulares compiladas y tablas de patrones por proveedor.
   - **Criterio de Adopción de LLM (Fase 2)**: Se evaluará incorporar un modelo LLM local o API únicamente si la tasa de correos no coincidentes supera el 10% y el valor de negocio justifica el costo por llamada.

### Positive Consequences

* **Costo Operacional Cero (CON-C3):** El parseo por regex se ejecuta íntegramente en la CPU local de Go en menos de 2 milisegundos por correo, con costo de \$0 USD por llamada.
* **Seguridad y Privacidad Estricta (QA-9):** Cero credenciales o contraseñas de correo en texto plano; se utilizan tokens OAuth2 revocables y ningún dato del usuario se envía a servicios de IA de terceros.
* **Respuesta en Tiempo Real (QA-5):** Gracias a Gmail Push e IMAP IDLE, las confirmaciones de reserva se detectan en segundos sin esperar ciclos de polling lentos.
* **Tolerancia a Ráfagas:** Los correos detectados emiten el evento `booking.discovered` hacia NATS JetStream, amortiguando picos de cancelaciones masivas (QA-3).

### Negative Consequences

* **Mantenimiento de Plantillas Regex:** Cuando una aerolínea o agencia cambia drásticamente el diseño de sus correos de confirmación, las reglas pueden no capturar los campos (mitigado con un stream de *dead letters* y alertas para incorporar la nueva variante en la tabla de patrones).

## Pros and Cons of the Options

### Opción 1: Polling con Parseo por LLM Comercial

* Good, because los LLMs entienden texto desestructurado sin necesidad de escribir expresiones regulares.
* Bad, because costo prohibitivo: procesar 500.000 correos en una disrupción a \$0.01/call costaría \$5.000 USD (violando totalmente CON-C3).
* Bad, because latencias de 1 a 3 segundos por petición de API externa.
* Bad, because riesgos de privacidad al enviar correos personales a APIs externas de terceros (violando QA-9).

### Opción 2: Subida Manual de Correos

* Good, because implementación trivial.
* Bad, because viola el requerimiento funcional FR-2 de captura y escaneo automatizado.
* Bad, because traslada la fricción operativa al usuario, degradando la usabilidad.

### Opción 3: Gmail Push / IMAP IDLE + Parser por Reglas en Go

* Good, because detección instantánea de correos vía push.
* Good, because procesamiento en milisegundos con costo \$0.
* Good, because respeta al 100% la privacidad del usuario sin compartir datos con terceros.
* Bad, because requiere mantener un catálogo de reglas de parseo para los proveedores principales.
