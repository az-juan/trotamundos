## ADR-014: Autenticación — JWT RS256 (Gateway emisor en Fase 0 → Identity/OIDC en Fase 2)

**Status**: Aceptado
**Fecha**: 2026-10-27
**Decidido por**: Equipo de arquitectura

### Contexto

El Gateway necesita emitir y validar tokens para autorizar a Web, Mobile y terceros (ADR-006). Pero
el Auth como servicio propio (**Identity**) recién se extrae en **Fase 2** (ADR-001). Quedaba sin
decidir **quién emite el JWT en Fase 0** y **cómo lo validan los servicios de dominio** sin crear un
acoplamiento de secreto compartido ni el riesgo de *confused deputy* (Newman ch.11).

### Decisión

**Fase 0 — el API Gateway es el emisor y validador ligero de tokens:**

- Emite **JWT con firma asimétrica RS256** (clave privada en secreto del Gateway).
- Expone una endpoint **JWKS** (`/.well-known/jwks.json`) con la clave **pública**.
- Los servicios de dominio validan cada token localmente contra la clave pública (sin secreto
  compartido, sin una llamada de ida y vuelta al emisor por request).
- Claims mínimos: `sub` (usuario), `aud` (audiencia/servicio), `scope`, `exp`, `correlation-id`.

**Fase 2 — se extrae Identity como IdP (OpenID Connect):**

- Identity emite los JWT (RS256, par de claves gestionado en Vault).
- El Gateway y los servicios cambian su validación al JWKS de Identity; el Gateway deja de emitir.
- Se añade login social (Google/Apple) y tokens de refresco con rotación.

| Aspecto | Fase 0 | Fase 2 |
|---------|--------|--------|
| Emisor del JWT | API Gateway | Identity (IdP OIDC) |
| Firma | RS256 (clave del Gateway) | RS256 (clave en Vault) |
| Validación | JWKS del Gateway | JWKS de Identity |
| Login social / OAuth | No | Sí (OIDC) |
| Secretos | Env (Fase 0) → Vault | Vault, rotación |

### Consecuencias

| Positivas | Negativas / Riesgos |
|-----------|---------------------|
| RS256 evita el secreto compartido: cada servicio verifica con la clave pública | En Fase 0 el Gateway es un punto central de emisión (mitigado: es stateless y escala horizontal) |
| Sin llamada de ida y vuelta por request para validar (stateless, cumple SLA 800 ms) | Un componente más de "confianza" a proteger (el Gateway) |
| Migración a Identity en Fase 2 es un cambio de JWKS, sin tocar dominio (los puertos lo absorben) | Reloj de los clientes debe estar sincronizado (JWT `exp`): mitigado con NTP |
| AuthZ fina en cada servicio (verifica `aud`/`scope`) evita el *confused deputy* | |

### Criterio de migración a Identity (Fase 2)

Extraer Identity cuando se cumplan **2 de 3**:
1. Se requiere login social / OAuth2/OIDC para terceros.
2. El equipo supera 8 devs y la gestión de auth descentralizada se vuelve cuello de botella.
3. Se necesita SSO entre experiencias (web + mobile + terceros) con un único IdP.

### Alternativas descartadas

- **HS256 (secreto compartido)**: obliga a repartir el secreto a todos los servicios → mayor superficie de filtración y difícil rotación. Se prefiere RS256 desde el inicio; el costo extra es mínimo y el salto a Identity es limpio.
- **Session cookies + validación en DB**: añade una llamada por request y un estado a replicar; rompe el "stateless" del Gateway y encarece el SLA.
