## ADR-003: Go como Lenguaje Principal

**Status**: Aceptado
**Fecha**: 2026-10-26
**Decidido por**: Equipo de arquitectura

### Contexto

Se evaluaron Go, Rust, Kotlin/Spring, Elixir, TypeScript, Java/Quarkus para el backend. Criterios: rendimiento (SLA 800 ms), concurrency (escáner de correo, llamadas a APIs), simplicidad operativa (startup, equipo pequeño), ecosistema de microservicios.

### Decisión

**Go 1.23+** como lenguaje único para todo el backend (servicios, gateway, web BFF, tooling).

- `go.work` para multi-module workspace.
- Binarios estáticos, sin runtime externo.
- Goroutines para concurrency I/O-bound (escáner de correo, llamadas a proveedores).

### Consecuencias

| Positivas | Negativas / Riesgos |
|-----------|-------------------|
| Binario único por servicio: deploy trivial (1 archivo + 1 config) | No tiene type system tan rico como Rust/Kotlin (mitigado: interfaces + linters) |
| Concurrency nativa: 100 goroutines = 100 conexiones IMAP sin threads | Ecosistema de ML/NLP más pobre (mitigado: LLM como API externa, no in-process) |
| GC predecible (STW < 1 ms): cumple SLA de 800 ms | Verbosidad en generics (mejorado en 1.18+) |
| Ecosistema de microservicios maduro: `chi`, `pgx`, `nats.go`, `clickhouse-go` | Pool de talento menor que Java/Python (mitigado: Go es top-5 en adopción) |
| Mismo lenguaje que NATS: sin overhead de interlingüístico | |

### Criterio de adopción de otro lenguaje

Agregar un servicio en otro lenguaje solo si:
1. El parser de correo se vuelve cuello de botella CPU-bound → **Rust** para ese microservicio.
2. El equipo de datos opera Python/Spark → **Python** para notebooks/ETL (no para servicios en prod).
