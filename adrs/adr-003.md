# ADR-003: Adopción de PostgreSQL 16 como Base de Datos Primaria Multifuncional con pgx y sqlc

* Status: accepted
* Deciders: Arquitecto de Software Principal de Trotamundos, Equipo Core de Ingeniería
* Date: 2026-10-28

Technical Story: [FR-1, FR-2, FR-5, FR-7, FR-9, QA-1, QA-2, QA-6, QA-12, QA-15, CON-C1, CON-C3, CON-5]

## Context and Problem Statement

Trotamundos requiere persistir datos con estructuras y requerimientos heterogéneos:
1. **Entidades centrales relacionales con integridad estricta (ACID)**: Viajes (`trips`), reservas (`bookings`), usuarios y perfiles de viajeros, donde las relaciones y claves foráneas son críticas para evitar inconsistencias de negocio.
2. **Datos semiestructurados y polimórficos de proveedores**: Confirmaciones crudas de correos electrónicos, respuestas JSON variables de APIs de aerolíneas (NDC/GDS), cadenas hoteleras y rentadoras de autos que evolucionan continuamente.
3. **Analítica de viajes y monetización inicial (FR-9, QA-15)**: Consultas agregadas sobre destinos populares, patrones de cancelación y proyecciones de demanda para partners comerciales.

El equipo cuenta con **conocimiento consolidado en PostgreSQL y lenguaje SQL**, pero dispone de presupuesto muy limitado ($\le \$100\text{ USD/mes}$, CON-C3) y un equipo pequeño (CON-C1). Desplegar y operar múltiples bases de datos heterogéneas especializadas (ej. PostgreSQL + MongoDB + ClickHouse) desde el inicio multiplicaría los costos de hosting y la carga operativa.

¿Qué estrategia y tecnologías de persistencia permiten unificar el almacenamiento relacional, documental y analítico inicial maximizando la productividad del equipo y minimizando el costo y las piezas móviles?

## Decision Drivers

* `QA-2`: Soporte eficiente y ágil para 15 millones de cuentas de usuario creadas e indexadas.
* `QA-6`: Latencia de consulta en panel web $\le 800\text{ ms}$ (búsquedas por ID y clave primaria en $< 50\text{ ms}$).
* `QA-12`: Testeabilidad y tipado estricto en el acceso a datos.
* `QA-15` & `FR-9`: Soporte de consultas analíticas pesadas sin contención sobre transacciones críticas.
* `CON-C1`: Aprovechamiento del conocimiento previo del equipo en PostgreSQL y SQL estándar.
* `CON-C3`: Presupuesto mensual mínimo, evitando el alquiler de múltiples bases de datos gestionadas.
* `CON-5`: Iteración II de ADD 3.0 (Funcionalidad primaria y selección de tecnologías).

## Considered Options

* **Opción 1:** Persistencia Políglota Compleja desde Fase 0 (PostgreSQL para datos relacionales + MongoDB para documentos de correos JSON + ClickHouse para analítica OLAP)
* **Opción 2:** Base de Datos NoSQL pura basada en Documentos (MongoDB / DynamoDB)
* **Opción 3:** PostgreSQL 16 como Motor Multifuncional Unificado (Tablas Relacionales ACID + Columnas `JSONB` con índices GIN + Vistas Materializadas para analítica) consumido vía `pgx/v5` y `sqlc`

## Decision Outcome

Chosen option: **Opción 3: PostgreSQL 16 como Motor Multifuncional Unificado con `pgx/v5` y `sqlc`**, porque cubre el 100% de las necesidades del sistema en Fase 0 dentro de un único motor probado, robusto y dominado por el equipo.

Se explotan las capacidades avanzadas de PostgreSQL 16:
- **Modelo Relacional**: Transacciones ACID para la consistencia entre viajes y sus múltiples reservas asociadas.
- **Modelo Documental (`JSONB`)**: Almacenamiento de payloads variables de correos y contratos externos en columnas `JSONB` indexadas con índices GIN, eliminando la necesidad de un cluster de MongoDB.
- **Analítica de Monetización (FR-9)**: Vistas materializadas (`MATERIALIZED VIEW CONCURRENTLY`) e índices compuestos particionados que permiten resolver las consultas de agregación comercial sin impactar las lecturas en caliente de los usuarios.
- **Acceso a Datos con `pgx/v5` y `sqlc`**: Se descartan los ORMs pesados como GORM. Con **`sqlc`**, el equipo escribe consultas en SQL estándar nativo de PostgreSQL y la herramienta compila código Go 100% type-safe, con verificación sintáctica en tiempo de build y rendimiento idéntico a consultas directas. El pool de conexiones se gestiona eficientemente con **`pgxpool`**.

### Positive Consequences

* **Costo Mínimo Consolidado (CON-C3):** Una sola instancia de PostgreSQL 16 (local en Docker para desarrollo o gestionada en DigitalOcean por \$15–\$25 USD/mes) atiende todo el almacenamiento, ahorrando cientos de dólares en licencias y hosting.
* **Máxima Velocidad de Desarrollo (CON-C1, CON-C2):** El equipo no pierde tiempo aprendiendo nuevas APIs de bases de datos no relacionales ni configurando drivers dispares.
* **Seguridad de Tipos sin Sobrecarga de ORM:** `sqlc` detecta errores de nombres de columna, tipos incompatibles o sintaxis SQL rota durante `go build`, eliminando errores en runtime y generando structs idiomáticos en Go.
* **Flexibilidad para Datos No Estructurados:** Las columnas `JSONB` permiten incorporar nuevos formatos de aerolíneas o cambios en plantillas de correo sin requerir migraciones de esquema bloqueantes en la base de datos.
* **Ruta de Migración Gradual:** Si la carga analítica de monetización supera los 5 millones de registros históricos, se habilitará la réplica analítica dedicada o ClickHouse en Fase 1 sin haber pagado de más en etapas tempranas.

### Negative Consequences

* **Riesgo de Contención si no se Diseñan Índices Adecuados:** Consultas analíticas pesadas mal planificadas podrían consumir recursos de CPU (mitigado con índices de cobertura, vistas materializadas pre-agregadas y timeouts de consulta estrictos de 10s en `context.Context`).
* **Mayor Volumen de Almacenamiento en JSONB:** Los documentos JSONB almacenan los nombres de los atributos repetidamente (mitigado por la compresión TOAST nativa de PostgreSQL).

## Pros and Cons of the Options

### Opción 1: Persistencia Políglota Compleja desde Fase 0

* Good, because cada motor está hiper-especializado en su carga de trabajo (MongoDB para JSON, ClickHouse para agregaciones OLAP masivas).
* Bad, because costo prohibitivo en infraestructura: contratar PostgreSQL gestionado + MongoDB Atlas + servidor ClickHouse supera ampliamente los \$200 USD/mes (violando CON-C3).
* Bad, because complejidad operativa inmanejable para 3–5 desarrolladores: sincronización de datos entre tres motores, backups heterogéneos y monitoreo triple (violando CON-C1).
* Bad, because duplicidad de esquemas y riesgo constante de inconsistencia de datos.

### Opción 2: Base de Datos NoSQL Pura basada en Documentos

* Good, because esquema flexible para absorber payloads de terceros.
* Bad, because modelar las relaciones complejas entre viajes, reservas cruzadas, viajeros y permisos compartidos en un modelo no relacional es propenso a inconsistencias severas.
* Bad, because transacciones multi-documento lentas y complejas.
* Bad, because no aprovecha el fuerte conocimiento previo del equipo en SQL y PostgreSQL.

### Opción 3: PostgreSQL 16 Unificado con pgx y sqlc

* Good, because un solo motor cubre relacional, documentos JSONB y analítica inicial.
* Good, because costo mínimo y operación trivial para el equipo.
* Good, because `sqlc` genera código Go type-safe a partir de SQL nativo sin la sobrecarga de un ORM.
* Good, because integridad referencial garantizada en el núcleo de viajes.
* Bad, because la analítica masiva tiene un límite de escala antes de requerir una réplica o almacén columnar dedicado.
