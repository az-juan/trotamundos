# ADR-004: Frontend Web Server-Rendered con Go templ + htmx + Tailwind CSS

* Status: accepted
* Deciders: Arquitecto de Software Principal de Trotamundos, Equipo Core de Ingeniería
* Date: 2026-10-28

Technical Story: [FR-1, FR-4, FR-5, FR-8, QA-6, QA-13, QA-14, CON-C1, CON-C2, CON-C3, CON-5]

## Context and Problem Statement

El panel de gestión de viajes de Trotamundos debe ofrecer a los viajeros una experiencia fluida, rápida e interactiva para visualizar sus itinerarios, explorar detalles de vuelos y hospedajes en un timeline y gestionar reservas manualmente. El requisito de rendimiento QA-6 exige un tiempo de respuesta de navegación web $\le 800\text{ ms}$, con un tiempo de primer despliegue útil (*First Contentful Paint*) óptimo.

El equipo está conformado por 3 a 5 ingenieros con **alto dominio de Go y backend**, pero sin especialistas dedicados en frameworks SPA complejos de JavaScript (como React, Angular o Next.js). Además, el presupuesto de servidores es mínimo ($\le \$100\text{ USD/mes}$) y el tiempo de salida al mercado es sumamente acotado (CON-C2). Desplegar y mantener un runtime adicional de Node.js en producción para renderizar una SPA o SSR añade consumo de memoria (150–300 MB extra por instancia), vulnerabilidades en dependencias npm y una barrera de contexto permanente entre frontend y backend.

¿Qué tecnología y enfoque de desarrollo frontend permite construir una interfaz web interactiva, moderna y ultra veloz maximizando las habilidades del equipo en Go y eliminando por completo Node.js del entorno de producción?

## Decision Drivers

* `QA-6`: Tiempo de respuesta en web $\le 800\text{ ms}$ (renderizado inicial y transiciones ultra veloces).
* `QA-14`: Experiencia visual coherente y optimizada para la web.
* `CON-C1`: Aprovechamiento del conocimiento del equipo en Go y tipado estricto, minimizando el cambio de contexto a JavaScript.
* `CON-C2`: Reducción drástica del tiempo de desarrollo para el MVP (cero configuración de bundlers complejos).
* `CON-C3`: Presupuesto mensual mínimo, eliminando el consumo de memoria y servidores de un runtime Node.js.
* `CON-5`: Iteración II de ADD 3.0 (Funcionalidad primaria y selección tecnológica).

## Considered Options

* **Opción 1:** Single Page Application (SPA) desacoplada en React / Next.js con backend como API JSON pura
* **Opción 2:** Renderizado clásico en servidor con el paquete estándar de Go `html/template` sin interactividad en cliente
* **Opción 3:** Server-Side Rendering Moderno con Go **`templ`** (componentes compilados a Go, type-safe) + **`htmx`** (~14 KB para interactividad dinámica y swaps de DOM) + compilación estática de **Tailwind CSS**

## Decision Outcome

Chosen option: **Opción 3: Server-Side Rendering con Go `templ` + `htmx` + Tailwind CSS**, porque permite a los desarrolladores de Go construir una interfaz de usuario interactiva y moderna escribiendo código Go tipado, sin necesidad de ejecutar Node.js en los servidores de producción.

- **`templ` (`github.com/a-h/templ`)**: Compila componentes de interfaz directamente a código Go estático. Si un desarrollador pasa un dato con tipo erróneo a un componente de UI, el compilador de Go arroja error en tiempo de build (`go build`). La renderización de HTML en memoria toma microsegundos.
- **`htmx`**: Biblioteca liviana de solo ~14 KB que se sirve como archivo estático. Permite realizar swaps parciales de fragmentos del DOM mediante atributos HTML declarativos (`hx-get`, `hx-target`, `hx-swap`), actualizaciones en tiempo real con Server-Sent Events (SSE) y modales sin escribir una sola línea de JavaScript complejo.
- **Tailwind CSS**: Se compila en tiempo de compilación mediante su binario CLI independiente a un único archivo CSS estático minificado ($< 30\text{ KB}$), eliminando dependencias de build en producción.
- **Cero Node.js en Producción**: El binario final de Go contiene embebidos los templates compilados y los assets estáticos, logrando un artefacto autocontenido desplegable en cualquier entorno.

### Positive Consequences

* **Primer Despliegue Instantáneo (QA-6):** El navegador recibe HTML ya renderizado con todos los datos del viaje en la primera respuesta. El *First Contentful Paint* es $< 250\text{ ms}$, eliminando la pantalla en blanco inicial y la pesada fase de hidratación de React/Angular.
* **Cero Node.js en Runtime (CON-C3):** Ahorro total de memoria RAM y CPU en el servidor; el binario Go atiende tanto las rutas web como las APIs con un consumo marginal.
* **Seguridad de Tipos de Extremo a Extremo (CON-C1):** Los modelos de dominio en Go se pasan directamente a los componentes de `templ` sin serializar ni deserializar JSONs intermedios en la web.
* **Velocidad de Iteración y Desarrollo (CON-C2):** Con `air`, cualquier cambio en un template de `templ` o archivo Go recarga el navegador automáticamente en menos de un segundo.

### Negative Consequences

* **Interactividad Offline Compleja Limitada:** No es adecuado si la aplicación web requiriera funcionar 100% offline sin conexión (no es el caso de Trotamundos, que es un panel conectado a la red).
* **Curva de Aprendizaje de `templ` y `htmx`:** Aunque es mínima para desarrolladores de Go (1–2 días), el equipo debe familiarizarse con la sintaxis de componentes `.templ` y los atributos de `htmx`.

## Pros and Cons of the Options

### Opción 1: Single Page Application (SPA) con React / Next.js

* Good, because ecosistema masivo de librerías de componentes UI listos para usar.
* Good, because estándar muy extendido en el mercado para frontend dedicado.
* Bad, because obliga a mantener dos stacks tecnológicos separados (Go en backend y Node.js/TypeScript en frontend), duplicando la fricción para un equipo de 3–5 desarrolladores (violando CON-C1).
* Bad, because requiere mayor consumo de memoria en el servidor para SSR en Node.js, aumentando el costo de hosting (violando CON-C3).
* Bad, because tiempo de carga inicial más lento debido a bundles de JavaScript de varios megabytes (afectando QA-6).

### Opción 2: Renderizado Clásico con html/template Estándar

* Good, because viene incluido en la librería estándar de Go sin dependencias de terceros.
* Bad, because los templates no están tipados: cualquier error en un nombre de variable o llamada a método solo se detecta en tiempo de ejecución al acceder a la página.
* Bad, because cada interacción del usuario (ej. filtrar viajes o abrir un detalle) exige recargar la página entera, generando una experiencia tosca y lenta.

### Opción 3: Go templ + htmx + Tailwind CSS

* Good, because componentes HTML compilados a Go con seguridad estricta de tipos.
* Good, because interactividad fluida tipo SPA mediante swaps parciales del DOM sin complejidad de JavaScript.
* Good, because el servidor genera y entrega el HTML completo en milisegundos, cumpliendo con creces el SLA de 800 ms de QA-6.
* Good, because cero Node.js y cero sobrecosto en servidores de producción.
* Bad, because para componentes altamente complejos en cliente (como un editor de mapas interactivo avanzado) se requiere recurrir a pequeños snippets de JavaScript vanilla o Alpine.js.
